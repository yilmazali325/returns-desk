# Clarification questions (send early) and the defaults we implement

The brief asks candidates to share clarification questions early so both receive the same answers.
Until we get answers, the system implements the default shown for each question. Each default is
the option least likely to cause a wrong business mutation.

| # | Question | Default we implement until answered |
|---|----------|-------------------------------------|
| 1 | **public_06:** after `timeout_after_commit`, our system queries the store in the same turn and confirms that the refund committed. Should turn 2 be `completed`, or do you expect `error`, with turn 3 the first `completed`? | Turn 2 is `completed` only when reconciliation finds the committed record (otherwise `error`). Turn 3 is a `completed` replay of the identical transaction with no new effects. |
| 2 | The customer asks for a specific exchange that is impossible: the size is out of stock or not offered, the price differs, it is the same size, or it is a different product. Other sizes are valid. Is the expected decision `deny`, or `clarify` with an alternative? | `deny` with proposal null. Valid alternatives appear in the reply text only. No alternative proposal is created. |
| 3 | The customer names an order that is not on their account, either another customer's or one that does not exist: `deny` or `clarify`? | `deny` with the same wording in both cases. Nothing about another customer is revealed. |
| 4 | "I want to **return** line L1", with neither refund nor exchange stated: propose a refund, or clarify the remedy? | "return" or "send back" alone means refund. We clarify only when refund and exchange wording both appear. |
| 5 | Exchange with no target size ("for a different size"): always clarify, or propose when only one valid size exists? | 2 or more valid sizes: clarify and list them. Exactly 1: propose it. None: `deny`. |
| 6 | Several of the customer's lines match the description, but only one of them is eligible: clarify, or propose the eligible one? | Clarify. Uniqueness is judged over all matching lines, whatever their eligibility. |
| 7 | After completion, the same request arrives again under the same `request_id`, either without `confirm_proposal` or with a repeated confirmation: `completed` (replay) or `deny`? What if it targets a different line? | Same target and same remedy: `completed`, returning the original result with zero new effects. A different target, or the other remedy on the completed line (an exchange after a completed refund): `deny` (request already completed). |
| 8 | A verbal "yes, go ahead" without the `confirm_proposal` flag: what decision? | `propose`, re-presenting the same proposal (same ID) and saying explicit confirmation is required. No mutation. |
| 9 | A turn has `confirm_proposal: "last"` but its text cancels or changes the request ("No, cancel", "Yes but size S instead"). Is the flag authoritative? | An explicit cancel or change phrase blocks execution, and the turn is handled as unconfirmed. Any other wording executes the bound proposal. A change counts when code reads it (cancel words, another remedy, size, line or order ID, or a product on the account other than the bound one: "Yes, refund the t-shirt" on a jeans proposal) or when the agent proposes something other than the bound proposal. A change that neither code nor the agent can read (a misspelled product name) still executes the bound proposal. |
| 10 | Should `turn.proposal` be null on `deny` and `completed` turns? Which field names does the grader read (for example `amount_cents`, `remedy`, `replacement_sku`)? | Proposal object only on `propose` turns, otherwise null. Field names follow the contract vocabulary: `proposal_id, request_id, customer_id, order_id, line_id, remedy, original_sku, replacement_sku, amount_cents, currency`. |
| 11 | May `final_state` contain extra top-level keys? Where should the stock_change "external event" go? | `final_state` keeps exactly the input keys. External events and proposals go at result level (`external_events`, `proposals`) and in `action_audit`. |
| 12 | Apple Silicon has unified memory. Should `peak_vram_mb` report the GPU's unified-memory allocation, or null? | The measured GPU unified-memory allocation (IOAccelerator, idle baseline subtracted), labelled `memory_architecture: "unified"`, with a note that it overlaps RAM. |
| 13 | Does "3 runs from a clean initial state" also require a fresh inference server or cleared prompt caches? | Business state resets before every case. Each run is a fresh adapter process with a fresh llama-server. The prompt cache persists within a run, and that is declared. |
| 14 | Is changing quantization (Q8_0 baseline → Q4_K_M final) acceptable if quality is shown to be preserved? | Yes. We also report a same-quantization comparison and a per-change ablation. |
| 15 | Will you run `python adapter.py` on your own machines, or on ours during the session? | On our machine. Setup for another Apple Silicon Mac is documented (pinned model revision and sha256). |
| 16 | A confirmed proposal fails the re-check at execution time, for example the replacement went out of stock before the confirmation (public_05 turn 2): `deny`, `error`, or `clarify` with the alternative? | `deny`. The proposal is invalidated and nothing changes. The reply explains why and lists valid alternatives in the text. The customer can pick one in the next turn, which creates a new proposal. |
| 17 | An order's `status` is spelled differently from the contract's `delivered`, e.g. `Delivered` or `delivered ` (review B6): does it count as delivered? | No. Only the exact value `delivered` is delivered; anything else is `NOT_DELIVERED` (deny). The desk's policy and the oracle use the same exact comparison. |
| 18 | A turn sets `confirm_proposal: "last"` but the conversation has no proposal yet, for example "Yes, go ahead and refund it" as the first turn: `clarify`, or treat the text as a new request and `propose`? | When no customer message names an item (an order, line, product or size), we `clarify` and ask which item, even on a one-item account: the customer is confirming something they think was offered, so "it" is not a request to guess at. When a message does name one, we treat the text as a new request (`propose`, `deny` or `clarify` as usual). Either way the flag is ignored because there is nothing to confirm, so nothing executes in that turn. |
